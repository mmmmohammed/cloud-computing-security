Module 05 — private cloud with Eucalyptus

The product was the API, not the hypervisor.

Eucalyptus is dead software with a live idea: implement Amazon's API on hardware you own, and every AWS tool, script and skill works unchanged. That is why banks and ministries wanted it, why OpenStack inherited the shape of it, and why the architecture is still worth an afternoon — a control plane is a control plane wherever it runs.

01

Open-source IaaS, built to be a drop-in for EC2

Elastic Utility Computing Architecture for Linking Your Programs To Useful Systems — a research project that answered a question nobody else had answered yet.

The short history, because the ending matters to your decision
2008First release. Began as research at the University of California, Santa Barbara — an open-source IaaS for private and hybrid clouds.
APIImplemented EC2, S3, EBS, IAM, Auto Scaling, ELB and CloudWatch-style APIs. AWS tools and scripts worked against it without modification.
2014Eucalyptus Systems acquired by HP; development later moved to AppScale.
TodayLargely legacy. New private clouds choose OpenStack, VMware or a public region — worth saying plainly rather than pretending otherwise.

The reason it is still studied is not nostalgia. It is the first clear demonstration that a cloud is a control plane plus a promise: the API contract is the product, and the hardware behind it is an implementation detail. Once you have seen that, "I know AWS" becomes a transferable claim instead of a vendor loyalty, and the same insight explains why Terraform, LocalStack and OpenStack all work the way they do.

It also settles the question module 03 raised: why a bank or a ministry would build this at all. Data residency, control of the hardware, and a compliance story you can point at — paid for with the obligation to secure every layer yourself.

02

Three levels, five controllers, and one of them matters most

Pick a component to see its job, and what an attacker gains by taking it.

The hierarchy: one cloud, many clusters, many nodes
LevelComponentJob
CloudCLCCloud Controller — the entry point. Exposes the APIs and console, authenticates users, makes high-level scheduling decisions.
CloudWalrus / OSGS3-compatible object storage: machine images, snapshots, user buckets.
ClusterCCCluster Controller — one cluster per availability zone: schedules VMs, manages virtual networking.
ClusterSCStorage Controller — block volumes and snapshots, the EBS equivalent.
NodeNCNode Controller — on every physical host; drives KVM or Xen to start, stop and inspect instances.

ask this in an interview

"Which component would you compromise first?" The CLC — not because it holds the data, but because it issues the credentials and decides where work goes. In AWS terms: the control plane, not the data plane. Attackers who want persistence take the thing that hands out permissions.

03

Every concept has an AWS twin, down to the naming

The compatibility was deliberate: same calls, same objects, different hardware underneath.

Eucalyptus mapped onto AWS
AWS serviceEucalyptus componentPurpose
EC2CLC + CC + NCLaunch and manage instances
S3Walrus / Object Storage GatewayImages, buckets, objects
EBSStorage ControllerPersistent volumes and snapshots
IAMEuareAccounts, users, groups, policies
AMIEMI, with EKI kernel and ERI ramdiskThe machine image triple used to boot
Availability ZoneClusterIsolated group of nodes — a failure domain
Security groups, key pairs, Elastic IPsSame concepts, same API callsFirewalling, SSH access, static addresses
ELB, Auto Scaling, CloudWatchEquivalent services in 3.3+Load balancing, scaling, monitoring

The image triple is the detail people miss. An AWS AMI is one identifier; a Eucalyptus image is an EMI plus a kernel (EKI) and a ramdisk (ERI), because the system boots the kernel you registered rather than the one inside the disk image. The lab prints all three per image for that reason.

04

Six hops between a command and a running machine

Trace it once and the diagram stops being a diagram.

euca-run-instances, end to end
StepWhat happensWhere it can fail
1The client sends a signed API request to the CLC.Bad signature, expired timestamp, unknown key — the refusals in section 10.
2The CLC authenticates, applies Euare policy, checks quota.Permission or quota — the most common 403 in a shared private cloud.
3The CLC picks a cluster with capacity and forwards the request.No capacity anywhere: the request queues or is rejected.
4The CC selects a node, allocates addresses, configures the network.Address exhaustion, network misconfiguration.
5The NC fetches the EMI from Walrus or its cache and boots it under the hypervisor.Missing image, unsupported kernel, hypervisor mismatch.
6State moves pending → running; the user connects with their key pair.Boot failure — visible only by watching the state, which is why the lab polls.

Notice where the signature check sits: step 1, before anything else. Authentication is not a feature of the application layer here, it is the price of entry to the control plane — the same conclusion module 04 reached from the other direction.

05

Querying it: euca2ools, then boto3 with an endpoint URL

One flag is the whole argument for API compatibility.

shell · euca2oolsfrom the deck

source ~/.euca/eucarc                  # endpoints and keys, issued by the CLC

euca-describe-availability-zones verbose   # free and maximum slots per cluster
euca-describe-images                        # EMI + EKI + ERI
euca-create-keypair lab-key > lab-key.pem  # private key shown once — chmod 400
euca-run-instances -k lab-key -t m1.small emi-1A2B3C4D
euca-describe-instances

python3 · boto3endpoint_url is the point

import boto3

ec2 = boto3.client(
    "ec2",
    endpoint_url="https://compute.mycloud.local:8773/",
    aws_access_key_id=KEY,
    aws_secret_access_key=SECRET,
    region_name="eucalyptus",
)
print(ec2.describe_instances())

The SDK does not know it is talking to a private cloud. Nothing in that snippet is Eucalyptus-specific except the URL and the region name — which is exactly what "AWS-compatible" bought: the ability to develop against a laptop or a private cloud and deploy to a public one without rewriting.

The credentials in eucarc deserve the same treatment as any AWS key: never committed, rotated, and issued per person rather than per team. The -k lab-key flag is the other half of it — the private key is displayed once, and if it lands in a shell history you have lost it.

06

Two browser extensions died; the CLI did not

A short history of tooling, and why the command line outlived the graphical ones.

Management tools
ToolWhat it didStatus
Euca2oolseuca-*, euare-*, euserv-* — scriptable CLI for Eucalyptus and AWSHistorical, still the clearest way to learn the API
ElasticFoxFirefox extension from Amazon for managing EC2 in the browserDiscontinued
HybridFoxFork that managed Eucalyptus and AWS from one panel — the hybrid-cloud pitch in a sidebarDiscontinued; modern browsers cannot run it
Eucalyptus consoleWeb console for users and administratorsHistorical
NowAWS Console and CLI, OpenStack Horizon and CLI, Terraform, LocalStack for offline practiceCurrent

The pattern is worth noticing: the graphical tools were the ones that needed a plugin runtime, and they died with it. The CLI and the SDK survived because they were thin clients over an HTTP API — the same reason module 04 could ask the same three questions of three clouds with three commands.

07

What survives what: the table the diagram does not give you

Private cloud means you own the failure domains too — and you should know them before the power cut.

If this dies, what still works
Component lostRunning instancesNew launchesOther clusters
CLCKeep runningImpossibleAlive, but unreachable — no API to ask
WalrusKeep runningStall at the image fetch unless cachedAlive; cached images may still boot
One CCKeep runningStop in that cluster onlyUnaffected
One SCKeep runningContinue without new volumesUnaffected
One NCInstances on that host stopReschedule unless the cluster is fullUnaffected
Power to one buildingEverything in that cluster stopsStop in that clusterContinue — separate failure domain

That last row is the Kaunti Health case in one line, and it is also the honest answer to "is a private cloud resilient?" It is exactly as resilient as the way you laid out clusters, power and network — no more, and nobody else's problem to fix.

08

NASA needed more, wrote its own, and started OpenStack

2008–2010, NASA Ames. The clearest case of a private cloud outgrowing its software.

NASA built Nebula, a private cloud for its scientists, and experimented with Eucalyptus. When the requirement outgrew what the software could do, NASA engineers wrote their own compute controller. In 2010 that code was combined with Rackspace's storage software and released as OpenStack — which now runs large private clouds, including CERN's and several telecom networks.

The lesson is not "Eucalyptus lost". It is that the control plane is an artefact you can build, fork or replace, and that doing so is a normal engineering response to a requirement no vendor meets. It is also a warning: a private cloud is a product you now maintain, with a roadmap you have to staff.

the security consequence

Private clouds give control and residency, and hand you every layer's security with it: patching the controllers, protecting the API endpoints, isolating tenants, and knowing that the responsibility matrix from module 03 has no provider column to hide in.

09

Two planes, two different jobs

Control plane failures are loud; data plane failures are quiet and worse.

Control plane

  • Restrict CLC, console and API ports to admin networks
  • TLS on every API endpoint — the signature protects integrity, not confidentiality
  • Rotate and protect credentials in eucarc files
  • Least-privilege Euare policies per department
  • Log and monitor all API activity centrally

Data plane

  • Patch hypervisors and node controllers promptly
  • Isolate tenant networks — VLAN or managed networking
  • Encrypt volumes and snapshots
  • Use hardened base images only
  • Physically secure the data centre — it is yours now

The split is the same one module 04 drew from the outside: the control plane answers "who may do what", the data plane answers "what happens when they do". In a private cloud you are the provider for both, and the audit findings below are what happens when the first one is left open.

Lab: I could not install Eucalyptus, so I built the part that mattered

An EC2-compatible control plane on localhost, with signatures verified server-side — and the same refusals a real one gives.

labs/week05 · minicloud.py, euca_client.py · logs: euca_client.log, mini_cloud.json

Why not the lab sheet's route

not run  The sheet offers two paths: a Eucalyptus FastStart VM, or LocalStack as an AWS-compatible substitute. FastStart images are no longer distributed — the project was archived years ago — and LocalStack needs Docker, which this machine does not have. Rather than write up a lab I did not do, I built the thing the module is actually about: a control plane that speaks the EC2 Query API, so the interesting questions stop being theoretical.

What I built

minicloud.py is 369 lines of standard library and comments: a threaded HTTP server on port 8773 — the port a real Cloud Controller listens on — implementing five EC2 actions in the EC2 XML envelope, plus Signature Version 4 verification on every request. The verification calls the signer written in module 04, so the code that signs is the code that checks: a mismatch is a real mismatch, not two bugs agreeing.

What the refusals prove

Measured · every request signed by the module 04 code
RequestStatusError codeWhy it matters
Signed correctly200—The contract works: same envelope, same signature, different cloud.
No Authorization header400MissingAuthenticationTokenRejected before authentication — the request never reaches the scheduler.
Signed with the wrong secret403AuthFailureThe header was parsed and the signature compared, then refused. This is the check that catches tampering and replay.

what this does not prove

It is not Eucalyptus, not a hypervisor, and not a private cloud anyone should run. There are no VMs — the instance states are timed transitions in memory. What it does prove is that the control plane is the interesting part, that I can implement one against a real API contract, and that I can verify signatures rather than merely generate them. The hypervisor work is still the next practical step.

Kaunti Health: a console on public Wi-Fi and one shared credentials file

A county health department, thirty clinics, twelve node servers, and an audit with two findings.

The facts, as the case gives them
EstateOne Cloud Controller, two clusters (one per building), twelve node servers, running patient-records and lab systems for 30 clinics.
ComplaintDoctors say new test servers take days to arrive.
Audit finding 1The Cloud Controller console is reachable from the county's public Wi-Fi.
Audit finding 2Several staff share one administrator credentials file.
Power cutBuilding B lost power; everything in that cluster stopped. Building A kept running.
ObligationPatient data; must comply with data-protection rules.

Rank by what an attacker can reach, and the console finding wins: the CLC authenticates and authorises everything, and it is answering on a network full of patients, visitors and staff phones. The shared credentials file removes the only remaining attribution — every action looks like every other administrator, so the log tells you what happened and not who did it.

The power cut is not a security failure; it is the architecture working. Two clusters are two failure domains, and the case documents exactly what section 07's table predicts. The fix for the first two findings — admin VLAN or VPN with TLS, individual Euare users, reviewable logs — is the same work as securing any control plane, which is why the module spends its time there.

12

Five questions on Kaunti Health

Scenario in section 11. Answer, then compare — each one has an explanation.

Q1Which component should be the top priority to protect?

C. The Cloud Controller. It is the entry point and controls the entire cloud — every credential, every scheduling decision. Losing it stops every operation, including the ones you would use to investigate.

Q2Each building's cluster behaves most like which AWS concept?

A. An Availability Zone. A cluster is an isolated group of nodes — a separate failure domain, which is exactly what an AZ is. A region would be the whole cloud.

Q3Which Eucalyptus component provides EBS-like volumes?

D. The Storage Controller. Block volumes and snapshots. Walrus is object storage (S3), Euare is identity (IAM), and the NC runs the hypervisor.

Q4The shared credentials file violates which principle most directly?

A. Accountability and least privilege. Shared credentials make actions untraceable to a person, and in practice leave everyone holding administrator rights they do not need.

Q5Why did Building A keep running during the power cut?

C. Separate failure domains. Each cluster — each building — is independent, like an Availability Zone. That is also why the CLC sitting in one building is a single point of failure worth planning around.

What I am taking from module 05

  1. 01A cloud is an API contract plus hardware; that is why skills move between providers and why private clouds were ever possible.
  2. 02The hierarchy — cloud, cluster, node — is also the failure hierarchy, and you choose it when you lay out buildings and power.
  3. 03The control plane is the prize: it issues credentials and decides placement. Protect it before you harden any VM.
  4. 04Compatibility is a strategy, not a feature — and it is why the CLI outlived every graphical tool built on the same API.
  5. 05Private cloud buys control and residency at the price of owning every layer's security, including the building.
