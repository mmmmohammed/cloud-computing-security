Module 04 — vendors, web services and APIs

Every action in the cloud is one signed HTTP request.

Launching a server, deleting a backup, reading a bucket: underneath, each one is an API call with an identity attached. That is why a stolen API key is worse than a stolen password — it is not one login, it is your whole permission set, scriptable. This module maps the vendors against each other, then implements the signature scheme that stands between the two.

01

Same building blocks, three sets of names

The vendors are not different products. They are the same eight primitives, branded differently — which is why a skill learned on one transfers to the others with a vocabulary list.

Equivalent services · AWS, Azure, Google Cloud
Capability AWS Microsoft Azure Google Cloud
Virtual machinesEC2Virtual MachinesCompute Engine
Object storageS3Blob StorageCloud Storage
Block storageEBSManaged DisksPersistent Disk
Identity and accessIAM, IAM Identity CenterEntra ID + Azure RBACCloud IAM
Virtual networkVPCVirtual Network (VNet)VPC
Key managementKMS, CloudHSMKey VaultCloud KMS
Threat detectionGuardDutyDefender for CloudSecurity Command Center
Serverless functionsLambdaAzure FunctionsCloud Run functions

Read the identity row twice. Every other capability is reachable through it, which is why the identity service is the one attackers study first — and why the responsibility matrix from module 03 never moves that row to the provider.

Beyond the big three there is Oracle Cloud Infrastructure, IBM Cloud and Alibaba Cloud. Two habits matter more than the list: service names change, so verify against current documentation rather than a slide; and the mapping is not one-to-one — two vendors' "equivalent" services can differ in limits, defaults and failure modes, which is where migration projects get hurt.

the interview answer

"They are the same primitives with different names and different defaults." Knowing the primitives is the transferable part; knowing the defaults is what stops you shipping an open bucket.

02

Choosing a vendor is six questions, and one of them is legal

Price is the least interesting of the six, because it is the one you can measure before you commit.

Vendor selection criteria
CriterionThe questionWhat it looks like from Kenya
Region and latency Where is the nearest region, and where are replicas and backups? South Africa hosts regions for AWS (Cape Town), Azure (Johannesburg, Cape Town) and Google (Johannesburg). Module 02's probe measured Cape Town at 84.8 ms against Ireland's 159.3 ms from this machine.
Compliance and certification Can the provider show the audit reports a regulator will ask for? ISO 27001, 27017, 27018, SOC 2, PCI DSS — obtainable through portals such as AWS Artifact rather than by emailing a salesperson.
Services and ecosystem Are the managed databases, AI and security tools you need actually available in your region? Newer services reach new regions later. A service that exists but not locally is a service you cannot use for data that must stay in-country.
Cost and billing currency What do compute, storage and egress cost, and how do you pay? Data transfer out is the line that surprises people; a card-only billing requirement is a procurement problem in many organisations.
Exit strategy How hard is it to leave, and what would leaving cost? Proprietary managed services raise the exit price. This is the lock-in question of module 03, priced.
Support and SLA What uptime is committed, and who answers at 3 a.m.? An SLA is a refund mechanism, not an availability mechanism. Your continuity plan has to survive the provider being down.

03

SOAP, REST, and the five verbs everything is built from

Cloud APIs converged on REST over HTTPS with JSON. The exceptions are old, and you still meet them.

SOAP

  • XML message inside an envelope, described by a WSDL contract
  • Strict typing and tooling; verbose on the wire
  • Survives in older enterprise systems and early cloud APIs
  • Security story: WS-Security, and a great deal of XML parsing to get wrong

REST

  • Resources addressed by URL, acted on with HTTP methods
  • Stateless: every request carries its own proof of identity
  • The default for AWS, Azure and Google Cloud control planes
  • Security story: the transport plus the signature on each call
HTTP methods and the status codes that matter in this module
MethodMeansStatusMeans
GETRead — must not change state200OK
POSTCreate400Malformed or missing parameter
PUTReplace401No valid identity presented
PATCHPartial update403Identity valid, permission missing
DELETERemove404Not found

The difference between 401 and 403 is the difference between "who are you" and "I know who you are, and no". The lab later receives a real 401 from AWS, and the reasoning is visible in the response body — which is still XML, because the EC2 Query API never moved to JSON.

Whatever the format, the security rules do not change: HTTPS only, authenticate every request, least privilege on the identity, and log every call. The eight fallacies apply here too — "the network is reliable" is why a call needs a timeout, and "the network is secure" is why a call needs its own authentication.

04

How AWS authenticates a request: five steps, one signature

Signature Version 4. The secret key never travels; what travels is proof that you hold it. These are the values my implementation produced, not an illustration.

The example below is AWS's own published test case: a bare GET / to example.amazonaws.com, signed with the example key pair from their documentation. Because the expected answer is published, agreeing with it is evidence — not a claim.

what signing does not fix

Signing proves the request was made by someone holding the secret key. It says nothing about whether that someone should have the key. Steal the secret and you can sign anything, correctly, for as long as the key lives — which is why the answer to a leaked key is rotation and scoping, not a longer key.

05

The CLI and the SDK are wrappers around the same API

Both sign requests for you. That convenience is also why people never learn what a 403 means.

The same three questions on three clouds
QuestionAWSAzureGoogle Cloud
Who am I right now? aws sts get-caller-identity az account show gcloud auth list
Which regions exist? aws ec2 describe-regions az account list-locations gcloud compute regions list
What storage can I see? aws s3 ls az storage container list gcloud storage buckets list

"Who am I" first, always. In an incident it is the difference between investigating the right identity and investigating your own laptop twice. In the Python SDK the same call looks like this, and the signing is invisible:

python3 · boto3from the deck

import boto3

ec2 = boto3.client("ec2", region_name="af-south-1")
for region in ec2.describe_regions()["Regions"]:
    print(region["RegionName"])

Two things follow. First, prefer temporary credentials — roles, SSO, instance profiles — over long-term access keys; a key in a script is a key in a backup, a screenshot and a chat message. Second, every one of these calls is logged in CloudTrail with a source IP and user agent, which is how an investigation is reconstructed.

06

Six families of standard, and what each one is actually for

Standards are how a security claim becomes checkable by someone who does not trust you.

Cloud standards and frameworks
BodyWhat it gives youWhere you meet it
NISTSP 800-145 (the definition), SP 800-144 (public cloud security and privacy), SP 800-210 (cloud access control), Cybersecurity Framework 2.0 (2024)Design reviews, federal and regulated procurement
ISO/IEC27001 (ISMS), 27017 (cloud-specific controls), 27018 (PII in public clouds)Certification a customer or regulator asks to see
Cloud Security AllianceCloud Controls Matrix, STAR registry of provider assessments, Security GuidanceComparing providers on controls rather than marketing
Industry rulesPCI DSS v4.0 for card data, SOC 2 attestation reportsPayments, and any B2B customer doing due diligence
CIS BenchmarksFree hardening baselines for AWS, Azure, Google Cloud, Kubernetes and operating systemsThe first hardening pass on any new account
Open standardsOCI images, OpenAPI for REST, Kubernetes, OAuth 2.0 and OpenID ConnectWhere portability and lock-in are decided

Two of these behave differently from the rest. CIS Benchmarks are prescriptive — you can apply them this afternoon. ISO 27001 is a management system, not a checklist of technical settings; passing an audit does not mean the account is hardened, and hardening the account does not pass an audit. Confusing the two is common and expensive.

07

One region failed, and customers could not even open the dashboard

7 December 2021, AWS us-east-1. The most instructive part is not the outage — it is the concentration.

An automated scaling activity triggered behaviour that congested AWS's internal network in us-east-1. The control plane degraded with it: many APIs and the console were impaired for hours, so customers could not reach the dashboards they would have used to see what was wrong. Consumer services and smart-home devices that depended on that region failed with it.

Module 02's probe makes the concentration concrete: of 10,755 IPv4 and IPv6 prefixes published by AWS, 1,506 belonged to us-east-1 — 14% of the address space in one region. Popularity is not a security control, but it is a blast radius.

What the outage teaches, in the language of the earlier modules
ObservationPrinciple behind it
The console failed with the APIYour recovery tool must not depend on the thing that is broken — the fallacy of a single dependency, applied to operations.
Devices stopped working when a region didAvailability is part of security: the A in CIA. Module 01 said a distributed system hides failure; here nothing hid it.
Scaling automation caused the congestionModule 02's elasticity case has a shadow: automation amplifies whatever it is told to amplify, including a mistake.

what to do about it

Know which of your services are single-region and say so out loud. Put the recovery path — runbooks, credentials, status page — somewhere that does not share the failure. And read provider post-incident reports: they are free case material written by the people who fixed it.

08

Pwani Logistics: a key on a shared drive, and a CEO worried about lock-in

Mombasa. Container tracking across East Africa. The scenario is the module's quiz, and it is not exotic.

The facts, as the case gives them
CustomersImporters in Uganda and Rwanda report the current system is slow — a latency complaint before it is anything else.
The codeA developer's scripts already call a cloud API, and store the access key and secret in the script on a shared drive "to make it easy for others".
The boardThe CEO wants the cheapest option now, and is worried about being trapped later.
The regulatorPersonal data is processed, and the company must show evidence of security controls.

Rank the risks and the answer is uncomfortable: the slow system is a product problem, and the shared drive is an incident. A long-term key in a shared script is every permission that key has, available to everyone with access to the share, with no second factor and no expiry — and no way to know who used it, because they all used the same identity.

The remediation is a sequence, not a slogan: deactivate and rotate the key; review the audit log for the window it was exposed; move to roles or SSO with short-lived credentials; put the remaining secrets in a secret manager; and add a check that fails the build if a key pattern appears in a commit.

Three ways to be told no

The second script makes read-only calls to three real endpoints and records exactly what comes back. No credentials are real: the key pair is AWS's published example.

Measured · labs/week04/api_probe.py
RequestStatusError codeWhat it means
ip-ranges.amazonaws.com, unsigned 200 — Public data. No identity asked for, 2.7 MB returned.
ec2 DescribeRegions, unsigned 400 MissingParameter Rejected at parameter validation, before authentication: “must contain the parameter AWSAccessKeyId”.
ec2 DescribeRegions, signed with the example key 401 AuthFailure The Authorization header was parsed and the credentials evaluated, then refused — because the key is a documentation example.

That third row is the useful one. The difference between 400 and 401 is the difference between a request the service could not read and a request it read, understood, and refused on identity — which is exactly the distinction a responder needs when triaging: a wall of 401s from one source IP is a credential problem worth chasing, a wall of 400s is usually a broken client.

what this does not prove

It does not prove I can operate a cloud account — the CLI, boto3 and CloudTrail half is still unexercised. It proves I can read a cryptographic specification, implement it against the published vector, and interpret a provider's error responses. Those are different skills, and this page does not blur them.

Five questions on Pwani Logistics

Scenario in section 08. Answer, then compare — each one has an explanation.

Q1What is the biggest immediate security problem?

B. Anyone with access to the share has the key and its full permission set, with no expiry and no way to tell who used it. It should be removed, rotated, and replaced with roles or temporary credentials.

Q2Where can Pwani download its provider's ISO 27001 and SOC 2 reports for regulators?

C. Providers publish third-party audit reports through a compliance portal. CloudTrail is the evidence of your own actions, not the provider's certifications.

Q3Which choice best reduces the CEO's lock-in worry?

B. Portable technology and a written exit plan reduce dependence on one vendor. Avoiding APIs is not possible — every action is an API call.

Q4In AWS SigV4, what is sent across the network with each request?

D. Only the key ID and the computed signature travel. The secret stays on the client and is used to derive a per-day signing key — which is what section 04's third step computes.

Q5An API call returns HTTP 403. This most likely means:

C. 403 means the identity was accepted and the permission was not. A missing resource is 404; a refused identity is 401.
