Module 08 — identity and access management

There is no office door to lock. Identity is the perimeter.

Anyone with valid credentials can reach the console from anywhere, so the question stops being “who is inside the network” and becomes “what is this principal allowed to do, on which resource, under which conditions”. This module implements AWS's documented evaluation order as a working engine, then audits a real case-study account and takes it from fourteen findings to zero.

01

Six building blocks, and the one that should be temporary

Every IAM design is a combination of these. Most breaches are a missing guard on one of them.

IAM building blocks
BlockWhat it isHow it goes wrong
Root userCreated with the account, unlimited power, recoverable only by email and phoneNo MFA, and an access key that never expires — the single worst credential in any account
Users and groupsNamed identities with passwords or keys; groups carry permissions users inheritOne identity shared by a team, so CloudTrail records a username instead of a person
RolesIdentities assumed temporarily by services, other accounts or federated usersA role described as “the app's permissions” that can read every bucket in the account
PoliciesJSON documents allowing or denying actions on resources — identity, resource, boundary, SCP"Action": "*", because it worked first time
STSShort-lived credentials issued when a role is assumedLong sessions with no re-authentication, so revocation means deleting the role
Organizations & Identity CenterMany accounts under guardrails; single sign-on for the workforceAn SCP written once and never tested, believed to be a control it is not

The table has a direction of travel: away from long-lived credentials. Users with keys are the legacy pattern; roles, federation and STS are the current one. Every breach in this module's reading starts with a credential that was not temporary.

02

Anatomy of a policy that is actually least-privilege

Five fields, and each one is a decision you can defend in a review.

policy · read one bucket, with MFA, from the officeidentity-based

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReportsBucketOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::finance-reports",
        "arn:aws:s3:::finance-reports/*"
      ],
      "Condition": {
        "Bool": {"aws:MultiFactorAuthPresent": "true"},
        "IpAddress": {"aws:SourceIp": "197.248.0.0/16"}
      }
    }
  ]
}
What each field is doing
FieldThe decision
EffectAllow or Deny — and a Deny wins from anywhere in the policy set
ActionTwo named API calls, not s3:*
ResourceTwo ARNs, because the bucket and its objects are different resources — a mistake that produces “access denied” for a policy that looks correct
ConditionMFA present and the request from one network range
SidA human-readable intent, so the next reviewer does not have to reconstruct it

The Resource line is where beginners lose an hour. s3:ListBucket acts on the bucket, s3:GetObject acts on the objects inside it. Granting arn:aws:s3:::finance-reports/* for both looks sensible and silently fails the listing. My engine has a case for exactly this, and it expects an explicit allow for the bucket ARN.

A role has two policies, and only one of them is about permissions

The policy above grants what a principal may do. A role additionally carries a trust policy, which answers a different question: who is allowed to become this role at all. Confusing the two is how people “fix” an access problem by widening trust, which hands the role to whoever the trust names — often a whole account.

trust policy · only this CI repository, only on its main branchassume-role

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {"Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"},
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"},
        "StringLike": {"token.actions.githubusercontent.com:sub": "repo:org/app:ref:refs/heads/main"}
      }
    }
  ]
}

This is the pattern that removes deployment keys entirely: the pipeline presents a token, the trust policy decides whether that token may become the role, and the session lasts minutes. The sub condition is the security-critical line — drop it and any branch of any repository in the organisation can deploy to production, which is a real and repeated finding.

03

Six steps, and step three ends the argument

This is not a mental model to admire — it is an algorithm, and section 08 implements it.

AWS policy evaluation order
StepWhat happensConsequence
1Authenticate — signature and credentials verifiedNo identity, no request
2Collect the policies that applyIdentity, resource, boundary, session, SCP
3Any explicit Deny, anywhereImmediate deny. No allow can rescue it
4SCP and permissions boundary must allowA guardrail narrower than the policy wins
5An identity or resource policy must allowEither side can grant
6OtherwiseImplicit deny — the default for everything

Two sentences carry the whole system. Explicit deny beats any allow, and anything not explicitly allowed is denied. Together they explain why an SCP guardrail is such a strong control — it does not need to enumerate what is permitted, only what is forbidden — and why adding a Deny is the safest way to remove a capability you cannot delete.

the deny that outlives its author

A Deny statement is permanent until someone removes it, and it silently wins over every future Allow someone adds. That is a feature in a guardrail and a trap in a cleanup: when access “mysteriously does not work”, search the policy set for Deny before rewriting the Allow.

04

RBAC and ABAC: roles scale badly, tags scale dangerously

The trade is between the number of policies and the number of things you must protect.

Role-based versus attribute-based access control
AspectRBACABAC
BasisJob role or group (Developer, Auditor)Tags and attributes on principals and resources (Project=Afya, Env=prod)
ExampleAuditors can read CloudTrailYou may start instances whose Project tag matches your own
ScalingMore roles and policies as teams growFewer policies; new resources inherit access through tags
RiskRole explosion, stale permissionsTag tampering — whoever can edit tags can grant access
In AWSGroups, roles, managed policiesConditions on aws:PrincipalTag and aws:ResourceTag

The ABAC risk is structural, not accidental. If access is decided by a tag, then ec2:CreateTags is an authorisation permission, and should be treated as one. My engine has a case that compares the principal's Project tag against the resource's — and a second case where they differ, which denies. Policy variables make that comparison possible: "${aws:ResourceTag/Project}" on the expectation side resolves against the request.

05

Federation: one person, one identity, no passwords to rotate

The strongest IAM control is the one that removes IAM users from the picture.

Federation options
OptionWhat it doesUse it when
SAML 2.0An enterprise IdP (Entra ID, Okta, AD FS) asserts the user; AWS issues a role sessionYou already have a workforce directory with MFA
OIDC / OAuth 2.0Token-based identity for apps — and for CI systems that deploy without stored keysA pipeline needs to deploy without a key in its secrets store
CognitoCustomer-facing sign-up and sign-in with social and enterprise optionsThe identities are your app's users, not your staff

The gains are the same four every time: one identity per person, central MFA, instant removal when someone leaves, and no IAM passwords to manage. That last one is underrated — a departed employee with an IAM user and a key is a live credential, which is precisely the finding the lab's audit opens with.

06

Seven practices, and the five tools that prove you followed them

Each tool answers a question that review alone cannot: what is actually used, and by whom.

Practices

  • MFA on root and every human identity
  • No root access keys; credentials stored offline
  • Roles and temporary credentials over long-term keys
  • Least privilege — start small, add deliberately
  • Groups and SSO, not per-user policies
  • Rotate or delete unused keys and users
  • SCPs to deny risky actions across accounts

Tools

  • Access Analyzer — resources shared outside the account; least privilege from activity
  • Credential report — users, key ages, MFA status in one table
  • Last accessed — which permissions were never used
  • Policy simulator — test a request before shipping the policy
  • CloudTrail — who did what, when, from where

The credential report is the one an auditor will ask for, because it makes the uncomfortable facts impossible to skim past: a row with MFA = false and a key 700 days old is a finding in a table, not an opinion. The lab builds that table from a model of the account, then scores the findings.

07

Capital One, 2019: one role, one SSRF, 106 million people

Every element of this breach is a lesson from sections 03 and 06, in order.

A misconfigured web application firewall on EC2 was vulnerable to server-side request forgery. The attacker used it to query the instance metadata service and receive the temporary credentials of the attached IAM role. That role could list and read far more S3 buckets than a WAF needed. Regulators fined the bank US$80 million; a class action settled for US$190 million.

Each step, and the control that breaks the chain
Step in the attackControl that breaks it
SSRF in a public-facing applicationInput validation and egress restrictions — the app never needed to reach the metadata address
Metadata service returns credentialsIMDSv2 (released late 2019): a token obtained by PUT, which simple request forgery cannot send
The role reads everythingLeast privilege on the role — the blast radius is the permission set, not the account
Stolen credentials used from an unusual placeDetection: GuardDuty and CloudTrail anomaly alerts, and a role that only ever appears in one region

Notice that three of the four controls are cheap and one is a purchase. The expensive part of this module is not the tooling; it is the discipline of writing a role that can do one thing, and the organisational tolerance for the “access denied” tickets that follow.

08

Lab: implement the evaluation order, then try to break it

The deck says “test policies with the simulator”. Without an account, the honest version is to build the simulator.

labs/week08 · iam_eval.py, cases.json, access_review.py, tumaini.json · logs: access_review.log

The lab sheet wants an AWS account: two users with MFA, a bucket policy, an EC2 role, a Deny that overrides an Allow, the policy simulator, and a credential report. No account exists, so no IAM object was created — no users, no bucket, no role, no console screenshots. What is run instead is the part that needs no account: an evaluator that implements all six documented steps, and an audit tool that stands in for the credential report and Access Analyzer.

The engine supports wildcards in actions and resources, NotAction and NotResource, resource policies with Principal, permissions boundaries, SCPs, policy variables, and the condition operators a review actually uses — Bool, StringEquals/Like, IpAddress, ArnLike, NumericLessThanEquals and Null.

24/24 decisions match the expectation

Where the engine is deliberately incomplete

A small evaluator is only useful if it is honest about its edges. These are the parts I did not implement, and what each one would change:

  • Set operators — ForAllValues and ForAnyValue on multi-valued keys, which change whether one bad value in a list of tags denies the request.
  • Session and principal policies — the policies passed at AssumeRole time, which can only narrow an existing grant.
  • The Organizations hierarchy — SCPs applied down a tree of OUs, where the effective permission is the intersection at every level.
  • Wildcards in Principal beyond ARN-shaped matching, and cross-account resource policies that in turn rely on the caller's identity policy.

None of these change the cases in the file, and all of them would matter in a real account. The list is the difference between “I wrote a simulator” and “I wrote the whole of IAM”.

what 24/24 does and does not mean

It means the engine agrees with the expectations I wrote from AWS's documented behaviour — deny precedence, guardrail order, both resource forms, condition semantics. It is not a conformance test against AWS: no request in this lab ever reached the service. Where the two could differ, the expectation is the part that would need checking against real IAM.

09

Two decisions, traced step by step

The same request shape, two different reasons for the answer — which is the point of a trace.

python3 iam_eval.py --explain "Explicit deny"deny

$ python3 iam_eval.py --explain "Explicit deny"
request: arn:aws:iam::111122223333:user/amina
  action   s3:DeleteObject
  resource arn:aws:s3:::finance-reports/2026/q3.pdf

  1. authenticate    principal arn:aws:iam::111122223333:user/amina
  2. collect policies 2 identity · 0 resource · 0 boundary · 0 SCP
  3. explicit deny   identity policy NeverDeleteReports

  decision: DENY — explicit deny in identity policy NeverDeleteReports

The evaluation stopped at step three and never looked at the allow that also matched. That is why the same user can still write to the bucket: the Deny names s3:DeleteObject and s3:DeleteObjectVersion, not the whole service. A Deny scoped too widely is how a “fix” becomes an outage.

python3 iam_eval.py --explain "ABAC"allow

$ python3 iam_eval.py --explain "ABAC"
  action   ec2:StartInstances
  resource arn:aws:ec2:af-south-1:111122223333:instance/i-0abc
  context  aws:PrincipalTag/Project = afya
  context  aws:ResourceTag/Project = afya

  1. authenticate    principal arn:aws:iam::111122223333:user/daniel
  2. collect policies 1 identity · 0 resource · 0 boundary · 0 SCP
  3. explicit deny   none
  4. guardrails      no SCP or boundary attached
  5. explicit allow  identity policy StartOwnProjectInstances

  decision: ALLOW — allowed by identity policy StartOwnProjectInstances

This one walks all five steps and the answer depends on a condition evaluated at step five: the principal's Project tag resolved against the resource's, through ${aws:ResourceTag/Project}. Change one tag and the same request goes to implicit deny — which the next case in the file asserts.

Lab: the Tumaini audit, scored and then remediated

Fourteen findings, three of them critical, and a measurement of what fixing them changes.

The deck's case study is an account in a known state: twelve staff on two shared users, root without MFA and with an active key, a developers group holding AdministratorAccess, a departed employee's key used two weeks ago, and a Lambda role with s3:* on every bucket. The review tool takes a model of that account and produces what the credential report and Access Analyzer would.

Two findings in that list are worth reading twice. The escalation one is not a policy-review opinion: the tool checks for nine documented privilege-escalation pairs — iam:PassRole with lambda:CreateFunction, iam:CreatePolicyVersion alone, iam:AttachUserPolicy, and so on — and AdministratorAccess matches all of them. The “exceeds what it uses” finding is the least-privilege diff: one action on one ARN, which is also the answer to the case study's second question.

The remediation is applied to the model, not to an account: MFA set, root stripped of keys, the departed user removed, the admin group replaced with a scoped policy, and the role rewritten to the one action it needs. Re-running the audit on the fixed model yields zero findings. That is a demonstration that the rules account for every finding — not a claim that a real account was cleaned.

root cannot be deleted

My first version of the fix deleted the root user, which is impossible — AWS does not let you. The remediation now keeps root, enables MFA and removes its access keys, which is the actual procedure. A model that lets you do the wrong thing is worse than no model.

11

The one-week plan the manager asked for

Ordered by what is being exploited right now, not by what is easiest to tick off.

Remediation in priority order
DayActionWhy first
1Disable the departed employee's key; pull CloudTrail for its use; enable root MFA and delete root access keysAn active credential outside the organisation and an unguarded root account are the only two things that can end the company this week
1Replace AdministratorAccess on Developers with a scoped policy; keep an MFA-protected break-glass roleRemoves nine escalation paths from four people at once
2Scope the Lambda role to s3:PutObject on loan-docs/*The application's blast radius becomes one bucket
3Enforce MFA for every human identity, then require it in policyStops password replay and stolen-session use
4–5Replace the two shared users with per-person identities, then start SSOAccountability — otherwise CloudTrail cannot answer “who”

The order is the answer to “what should be done first”, and it is not the same as the order the findings are printed in. A key held by someone who has left is an incident; a 385-day-old key belonging to a current employee is a task. Both are findings; only one is on a clock.

12

Five questions on the audit

Scenario in the deck's case study, and in section 10.

Q1What should be done FIRST?

B. An active credential outside the organisation plus an unguarded root account are the two findings that can end the company this week. Everything else is a task; these are an incident.

Q2The correct permission for the Lambda role is:

D. One action, on the objects of one bucket. The function writes loan documents; it has no business reading, listing or deleting anything, and no business in any other bucket.

Q3Shared IAM users mainly break:

B. The audit trail records the username, never the human. That destroys both investigation and the ability to revoke one person's access without breaking a shift.

Q4A policy Allows s3:DeleteObject and an SCP Denies it. The result is:

D. Step three: an explicit deny anywhere ends the evaluation. The engine returns that decision at step three and never reaches the allow.

Q5Which tool shows which permissions developers have not used in 90 days?

A. Last-accessed data and Access Analyzer are the two sources that turn “might be unused” into a defensible decision. The review tool's key-age and last-used columns are the local stand-in for them.

13

What I am taking from module 08

  1. 01Identity is the perimeter, and long-lived credentials are the whole risk — root keys, shared users, 700-day-old keys.
  2. 02Explicit deny beats any allow, and everything else is implicitly denied. Those two sentences are the algorithm.
  3. 03An admin group is not one finding; it is nine escalation paths, and a policy check finds them faster than a review.
  4. 04Least privilege is measurable: one action on one ARN, and a diff you can show someone.
  5. 05Prioritise by what is being exploited now — a departed employee's live key outranks a year-old key on a current one.
  6. 06Federation is the end state: no IAM users means nothing to share, rotate or forget to delete.
