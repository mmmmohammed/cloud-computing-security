01 The road to cloud

Computing swings like a pendulum — and security moves with it

Centralised mainframe, decentralised PC, centralised cloud again. Each swing changes where the perimeter sits, who holds the data, and therefore which controls you can even apply.

1960s–70s

Mainframes & time-sharing

One powerful central computer; many users on dumb terminals. Centralised control, very high cost.

Pendulum: fully centralised
1980s

PCs & client–server

Computing moves to desks. Servers provide files, mail and databases to client PCs over LANs.

Pendulum: decentralised
1990s

Internet & clusters

The web connects everything. Clusters of cheap servers replace single big machines.

Scale out replaces scale up
2000s

Grid & utility

Grids share resources across institutions (CERN's LHC grid). Utility computing bills like electricity.

Billing becomes a design constraint
2006–2010s

Cloud computing

AWS launches S3 and EC2 (2006); Azure and Google follow. Self-service, pay-per-use infrastructure.

Pendulum: centralised again
Today

Edge, serverless & AI

Containers, serverless functions, IoT and edge nodes; GPU clouds power AI workloads.

Processing pushed back out
security lens

Every pivot relocates the trust boundary. On a mainframe you guarded one room; on client–server you guarded a LAN; in the cloud the perimeter dissolves into identity, API calls and configuration. That is why the rest of this course is mostly about IAM, storage policies, network paths and posture — not firewalls at the edge.

02 Definition

What a distributed system actually is

A collection of independent computers that appears to its users as a single coherent system. Tanenbaum & van Steen — the definition the whole module is built on
01

Resource sharing

Hardware, data and services are shared across machines — one database serving many web servers.

02

Concurrency

Many components run at the same time and must coordinate access to shared data.

03

Scalability

Add more machines (scale out) to handle more users rather than buying one bigger machine.

04

Fault tolerance

The system keeps working when individual nodes fail, using replication and redundancy.

05

No global clock

Each node has its own clock; ordering events needs logical clocks or synchronisation (NTP).

06

Transparency

Complexity is hidden: users do not see where data lives or which server answered.

security lens

No global clock is the quiet one. If nodes disagree on time, log correlation breaks, token expiry drifts, and an attacker can replay a request inside a window that two servers judge differently. Reliable NTP is a security control, not housekeeping.

03 Illusion

Six forms of transparency — and what each one hides

Transparency is the magic trick that makes many machines look like one. It is also what lets a compromised component stay invisible while the service still looks healthy.

ACCESS

Same call, local or remote

A mapped network drive looks like a local disk. Hides: whether the bytes ever left your machine.

LOCATION

You never know where it is

A URL hides the server's location. Hides: data sovereignty — which country holds the replica.

MIGRATION

Resources move silently

A live-migrated VM keeps serving. Hides: that the host, hypervisor and network path all changed.

REPLICATION

Many copies, one resource

Several copies exist for speed and reliability. Hides: replication lag and stale reads.

CONCURRENCY

Shared without collision

Two tellers update different accounts without interfering. Hides: race conditions and lost updates.

FAILURE

Faults are masked

A failed server is replaced and the user retries. Hides: that you were attacked rather than unlucky.

04 Structure

The three-tier model is the backbone of cloud apps

Presentation, application, data. Split the tiers and each becomes a separate attack surface with its own controls — which is the whole reason cloud security is layered.

Tier 1 · presentation

Browser / mobile app

Shows data and collects input. Runs on the user device or a CDN.

CloudFront · S3 static hosting
Tier 2 · application

Business logic & APIs

Web/app servers, APIs and microservices behind a load balancer.

EC2 · Lambda · ECS
Tier 3 · data

Databases, caches, objects

Replicated for availability — and the most valuable target in the system.

RDS · ElastiCache · S3
  • Client–server — clients request, servers respond (email, web)
  • Peer-to-peer — every node is client and server (BitTorrent, blockchain)
  • Service-oriented — services talk via standard interfaces (SOAP/REST)
  • Microservices — many small, independently deployed services (Netflix, Uber)
  • Event-driven — components react to messages on queues or streams
security lens

Each split tier is a new trust boundary. More services means more identities, more keys, more network paths and more ways to misconfigure a bucket. Microservices make the blast radius smaller and the visible attack surface bigger at the same time.

05 Comparison

Cluster, grid, utility, cloud, edge

Cloud borrows from all of them: clusters inside data centres, grid-style sharing, utility-style billing.

Comparison of distributed computing paradigms
Paradigm Ownership & control Coupling Typical use Example
Cluster One organisation, one site tight · fast LAN High-performance computing, databases University HPC cluster; Hadoop cluster
Grid Many organisations share resources loose · across WAN Large science projects CERN Worldwide LHC Computing Grid
Utility Provider owns, customer meters use loose Pay-per-use compute and storage Early IBM and Sun on-demand offers
Cloud Provider owns, self-service via API virtualised · elastic Almost any IT workload AWS, Microsoft Azure, Google Cloud

07 Real life

Netflix: designing for failure on purpose

Streaming · 2008 → 2016

One corrupted database took down DVD shipments for three days

Netflix ran its own data centres. A 2008 database corruption stopped DVD shipments for three days — a textbook single point of failure. Over the following years the company rebuilt the platform as hundreds of microservices across many AWS servers and Availability Zones.

Then it went further: engineers built Chaos Monkey, a tool that randomly terminates production instances, to prove the system survives. The wider Simian Army tested larger failures, including losing an entire zone.

Lesson: assume components will fail and test it deliberately. Resilience is a design property, not luck — the same mindset underpins incident response and disaster recovery.

08 Conclusion

From distributed computing to cloud computing

Cloud is not a new technology. It is a business and delivery model built on decades of distributed-systems research.

  1. Distributed systems

    Independent machines cooperate over a network.

  2. Virtualisation

    One physical server runs many isolated virtual machines.

  3. Resource pooling

    Thousands of servers form one shared pool of capacity.

  4. Automation & APIs

    Software provisions resources in seconds, with no human ticket.

  5. Metered self-service

    Customers pay only for what they use — that is the cloud.

security lens

Automation and APIs are what make cloud fast to break at scale. A console click can expose a bucket to the internet in seconds, and an API key can do it a thousand times before anyone notices. That is why posture management and detection arrive later in this track.

09 Lab evidence

I broke my own client on purpose — and kept the tracebacks

The lab asks for latency to cloud regions, a socket client and server, then stopping the server mid-session to see what happens. Below is the real output from this machine, including the failures. Failing loudly, then fixing it, is the point of the exercise.

1 · Regional latency — TCP handshake to port 443, 5 samples each labs/week01/probe_regions.py
Endpoint Resolved IP Min Avg Jitter Relative
AWS af-south-1 · Cape Town 52.95.176.26 80.4 ms 83.5 ms 1.8 ms
AWS eu-west-1 · Ireland 3.5.64.195 189.0 ms 193.6 ms 2.6 ms
AWS us-east-1 · N. Virginia 16.15.236.220 212.4 ms 217.1 ms 4.7 ms
Azure · South Africa North — ✕ DNS resolution failed no route

Cape Town is 2.3× faster than Ireland from here (83.5 ms vs 193.6 ms), and the difference is nearly all distance — constant packet count, growing RTT. That is fallacy 02 in numbers: latency is never zero, and it is a physical property of where you deploy.

2 · The failure client_crash.log

Server stopped mid-session. The naive client has no timeout and no retry, so the kernel's refusal becomes an unhandled exception and the program dies.

python3 socket_client_naive.py 
$ python3 socket_client_naive.py
Traceback (most recent call last):
  File "socket_client_naive.py", line 5, in <module>
    s.connect(("127.0.0.1", 9009))   # no timeout, no retry
ConnectionRefusedError: [Errno 111] Connection refused

Everything worked one minute earlier. That is the whole trap of "the network is reliable": the code was correct, and still crashed.

3 · The fix — timeout + bounded retry client_retry_recover.log

Three attempts, 2 s deadline per attempt, linear backoff. Same dead server, different outcome: the client survives and recovers the moment the server comes back.

python3 socket_client_retry.py 
$ python3 socket_client_retry.py
[client] attempt 1 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 2 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 3: reply: b'ACK:HELLO DISTRIBUTED WORLD'

Note what changed: not the network, not the server. Only the client's assumptions. Retry logic is availability engineering — and availability is a security property.

4 · Retry against a server that never returns client_retry_fail.log

Retries are not magic. With no upstream, the client gives up cleanly instead of hanging forever:

python3 socket_client_retry.py 
[client] attempt 1 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 2 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 3 failed: ConnectionRefusedError(111, 'Connection refused')
[client] giving up after retries

A bounded failure is a feature. Unbounded retries turn one dead dependency into a self-inflicted denial of service — the difference between resilience and a retry storm.

5 · Reflection answers
  • Which fallacy did the crash expose? The network is reliable — and its twin, that topology does not change. The failure was a stopped process, not a broken cable.
  • What did the retry add? Explicit timeout (latency is not zero) plus bounded attempts (so failure stays affordable).
  • Transparency provided: access transparency — I called connect() without caring whether the peer was local or remote.
  • Transparency missing: failure transparency and relocation. Nothing masked the outage, and nothing moved the request to a healthy replica, because there was no replica.
  • Why the Azure row failed: DNS could not resolve the endpoint in this environment. A name that does not resolve is an availability failure before any TCP packet exists — the first link in the chain is always name resolution.
security lens

The same three lines — timeout, bounded retries, backoff — are what stop an outage from becoming a credential-stuffing amplifier. Retry storms against an auth service are indistinguishable from a brute-force attack until you look at the client. Build the limit before the attacker does.

10 Check yourself

Five questions from the SACCO case study

Jamii SACCO, 40,000 members, one back-office server that died during dividend payouts. Pick an answer — the explanation appears either way.

Q1 Which characteristic of distributed systems does the replicated database in Nairobi mainly provide?

B. A second copy at another site lets withdrawals continue if one site fails — fault tolerance through replication. It is not a clock, and it does not hide anything from the user.

Q2 Members should not know which of the three application servers answered them. This is an example of:

A. The load balancer hides which replica — and where — served the request: location plus replication transparency.

Q3 The ICT officer's view on encryption reflects which fallacy?

D. Assuming the internal network is safe ignores insiders, malware and sniffing. Traffic between servers should still be encrypted and mutually authenticated.

Q4 Adding more application servers to handle December peaks is called:

A. Adding more machines of similar size is horizontal scaling. Vertical scaling would be buying one bigger machine.

Q5 Which architecture best describes the vendor's proposal?

D. Mobile app (presentation), app servers (logic) and database (data) form a three-tier design. The group discussion that follows is the interesting part: what new risks does a second site introduce?
