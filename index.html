Module 01 — distributed computing

Before you can secure a cloud, you have to know what it is.

Every service in this track — a bank app, a mobile-money wallet, an exam portal — is a distributed system: independent machines pretending to be one. This module covers the six eras that led here, the properties that hold that illusion together, and the eight fallacies that explain why cloud services fail and where attackers aim.

01

Computing swings like a pendulum, and security moves with it

Centralised mainframe, decentralised PC, centralised cloud again. Each swing changes where the perimeter sits and who holds the data.

Six eras of computing, 1960s to today
Era Model What changed Direction
1960s–70s Mainframes and time-sharing One powerful central computer, many users on dumb terminals. Centralised control, very high cost. centralised
1980s PCs and client–server Computing moves to desks. Servers provide files, mail and databases to client PCs over LANs. decentralised
1990s Internet and clusters The web connects everything; clusters of cheap servers replace single big machines. scale out
2000s Grid and utility Grids share resources across institutions (CERN's LHC grid); utility computing bills like electricity. pooled
2006–2010s Cloud computing AWS launches S3 and EC2 in 2006; Azure and Google follow. Self-service, pay-per-use infrastructure. centralised
Today Edge, serverless, AI Containers, functions, IoT and edge nodes; GPU clouds power AI workloads. pushed outward

security impact

Every pivot relocates the trust boundary. On a mainframe you guarded one room; on client–server you guarded a LAN; in the cloud the perimeter dissolves into identity, API calls and configuration. That is why the rest of this track is mostly IAM, storage policy, network paths and posture — not firewalls at the edge.

02

A distributed system is independent machines pretending to be one

A collection of independent computers that appears to its users as a single coherent system.

Tanenbaum & van Steen — the definition everything else is built on

Six properties do the pretending. They are also the six places where a design can quietly break.

Properties of a distributed system
Property What it means in practice When it fails
Resource sharing Hardware, data and services used across machines — one database serving many web servers. Contention; one noisy consumer starves the rest.
Concurrency Many components run at once and must coordinate shared data. Race conditions, lost updates.
Scalability Add machines (scale out) instead of buying a bigger one. State that cannot be partitioned becomes the ceiling.
Fault tolerance Replication and redundancy keep the service up when a node dies. Replication lag, split brain.
No global clock Every node keeps its own time; ordering needs logical clocks or NTP. Log correlation breaks; token expiry drifts.
Transparency Complexity is hidden: which server answered, where data lives. You cannot see the component that was compromised.

security impact

No global clock is the quiet one. If nodes disagree on time, an attacker can replay a request inside a window that two servers judge differently. Reliable NTP is a security control, not housekeeping.

03

Transparency is the trick — and what it hides is the risk

Six forms of transparency make many machines look like one. Each also hides something an incident responder needs.

Forms of transparency and the information each one withholds
Form What the user experiences What is hidden
Access A mapped network drive behaves like a local disk. Whether the bytes ever left the machine.
Location A URL resolves to a service, not a server. Sovereignty — which country holds the replica.
Migration A live-migrated VM keeps serving. That host, hypervisor and network path all changed.
Replication Many copies behave as one resource. Replication lag and stale reads.
Concurrency Two tellers update different accounts without collision. Race conditions and lost updates.
Failure A failed server is replaced and the user retries. That you were attacked rather than unlucky.

04

Three tiers, three attack surfaces

The n-tier model is the backbone of most web and cloud applications. Split the tiers and each becomes its own security problem.

Three-tier model mapped to cloud services
Tier Runs Typical service Main exposure
Presentation Browser or mobile app; shows data, collects input. CloudFront, S3 Client-side trust; cached private content.
Application Business logic, APIs, microservices behind a load balancer. EC2, Lambda, ECS Identity: keys, roles, unauthenticated endpoints.
Data Databases, caches, object storage; replicated for availability. RDS, ElastiCache, S3 The most valuable target in the system.

Other architectural styles you will meet: client–server (email, web), peer-to-peer (BitTorrent, blockchain), service-oriented (SOAP/REST interfaces), microservices (many small independently deployed services) and event-driven (components reacting to queues and streams).

security impact

Each split tier is a new trust boundary: more identities, more keys, more network paths, more ways to misconfigure a bucket. Microservices shrink the blast radius and enlarge the visible attack surface at the same time.

05

Cluster, grid, utility, cloud, edge

Cloud borrows from all of them: clusters inside data centres, grid-style sharing, utility-style billing.

Distributed computing paradigms compared
Paradigm Ownership Coupling Example
Cluster One organisation, one site Tight, fast LAN University HPC; Hadoop cluster
Grid Many organisations share resources Loose, across a WAN CERN Worldwide LHC Computing Grid
Utility Provider owns, customer meters use Loose Early IBM and Sun on-demand offers
Cloud Provider owns, self-service via API Virtualised, elastic AWS, Azure, Google Cloud
Edge / fog Distributed near users or devices Loose, latency-sensitive Smart-meter gateways; CDN edge nodes

06

Eight assumptions, eight ways in

Peter Deutsch and colleagues at Sun listed the assumptions designers wrongly make. Each one is also a control you forgot to configure.

  1. 01

    The network is reliable

    Reality: links fail, packets drop.

    Design for retries and failover. Availability is part of security — a service that is down cannot enforce anything.

  2. 02

    Latency is zero

    Reality: every call takes time.

    Timeouts get abused for denial of service. An unbounded wait is resource exhaustion — measure the handshake, then set a deadline.

  3. 03

    Bandwidth is infinite

    Reality: links saturate.

    DDoS exploits exactly this limit. Rate limits, autoscaling caps and egress quotas are security controls.

  4. 04

    The network is secure

    Reality: traffic can be sniffed or altered.

    Encrypt in transit and authenticate every call. “It is an internal network” is how lateral movement succeeds.

  5. 05

    Topology does not change

    Reality: nodes come and go constantly.

    Asset inventories go stale and unknown assets go unpatched. Cloud needs continuous discovery, not last quarter's spreadsheet.

  6. 06

    There is one administrator

    Reality: many teams and providers.

    Unclear responsibility causes misconfiguration. Shared responsibility only works when every control has a named owner.

  7. 07

    Transport cost is zero

    Reality: data transfer costs money.

    Egress fees and exfiltration both cost you. A sudden egress spike is often the cheapest early signal that data is leaving.

  8. 08

    The network is homogeneous

    Reality: mixed devices and protocols.

    The weakest component sets the security level. One legacy protocol defeats strong crypto everywhere else in the path.

07

Netflix moved to AWS because of one database

In 2008, a corrupted database stopped DVD shipments for three days. The company was running its own data centres.

Netflix rebuilt the platform as hundreds of microservices across many AWS servers and Availability Zones — then went further. Engineers built Chaos Monkey, a tool that randomly terminates production instances, to prove the system survives. The wider Simian Army tested larger failures, including losing a whole zone.

The lesson is not “use AWS”. It is that resilience is a design property, not luck: assume components will fail and test it deliberately. The same mindset runs through incident response and disaster recovery later in this track.

case study, applied

Jamii SACCO, 40,000 members, one back-office server that died during dividend payouts. The vendor proposes three application servers behind a load balancer and a replicated database in a second town. The ICT officer objects to encryption between servers: “our office network is private.” That sentence is fallacy 04, and it is why the design fails review.

08

Five steps from distributed computing to cloud

Cloud is not a new technology. It is a business and delivery model built on decades of distributed-systems research.

  1. Distributed systemsIndependent machines cooperate over a network.
  2. VirtualisationOne physical server runs many isolated virtual machines.
  3. Resource poolingThousands of servers form one pool of capacity.
  4. Automation and APIsSoftware provisions resources in seconds, with no human ticket.
  5. Metered self-serviceCustomers pay only for what they use — that is the cloud.

security impact

Automation and APIs are what make cloud fast to break at scale. A console click can expose a bucket to the internet in seconds; an API key can do it a thousand times before anyone notices.

2 — The failure

The server was stopped mid-session. The naive client has no timeout and no retry, so the kernel's refusal becomes an unhandled exception and the process dies.

socket_client_naive.pystderr

$ python3 socket_client_naive.py
Traceback (most recent call last):
  File "socket_client_naive.py", line 5, in <module>
    s.connect(("127.0.0.1", 9009))   # no timeout, no retry
ConnectionRefusedError: [Errno 111] Connection refused

It worked a minute earlier. That is the trap of “the network is reliable”: the code was correct and still crashed.

3 — The fix

Three attempts, a two-second deadline per attempt, linear backoff. Same dead server, different outcome:

socket_client_retry.pyrecovered

$ python3 socket_client_retry.py
[client] attempt 1 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 2 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 3: reply: b'ACK:HELLO DISTRIBUTED WORLD'

Nothing changed on the network or the server — only the client's assumptions. And when the server never returns, the same client gives up cleanly after three attempts instead of hanging: a bounded failure is a feature, because unbounded retries turn one dead dependency into a self-inflicted denial of service.

socket_client_retry.pyno upstream

[client] attempt 1 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 2 failed: ConnectionRefusedError(111, 'Connection refused')
[client] attempt 3 failed: ConnectionRefusedError(111, 'Connection refused')
[client] giving up after retries

4 — Reflection

Which fallacy did the crash expose? The network is reliable, and its twin that topology does not change — the failure was a stopped process, not a broken cable. What did retry add? An explicit deadline (latency is not zero) and a bounded number of attempts (so failure stays affordable). Transparency provided: access — the client called connect() without caring whether the peer was local or remote. Transparency missing: failure and relocation. Nothing masked the outage and there was no replica to move the request to, because the lab had exactly one server.

security impact

Timeout, bounded retries and backoff are the same three lines that stop an outage becoming a credential-stuffing amplifier. A retry storm against an auth service is indistinguishable from a brute-force attack until you look at the client.

10

Five questions on the SACCO case

Answer, then read the explanation. The score is for you, not for the page.

Q1Which characteristic does the replicated database in Nairobi mainly provide?

B. Fault tolerance. A second copy at another site lets withdrawals continue when one site fails. It is not a clock, and it hides nothing from the user.

Q2Members should not know which of the three application servers answered them. That is:

A. Location and replication transparency. The load balancer hides which replica, and where, served the request.

Q3The ICT officer's view on encryption reflects which fallacy?

D. The network is secure. Assuming the internal network is safe ignores insiders, malware and sniffing. Traffic between servers should still be encrypted and mutually authenticated.

Q4Adding more application servers for the December peak is called:

A. Scaling out. More machines of similar size is horizontal scaling; vertical scaling would be buying one bigger machine.

Q5Which architecture best describes the vendor's proposal?

D. Three-tier client–server. Mobile app, app servers and database form the three tiers. The better discussion is what the second site adds: replication lag, conflicting updates and a larger attack surface.
